\subsection{Program Facts and Datalog}

Program facts are structured representations of source code information used for automated reasoning. They encode observable properties of a program, such as entities (e.g., functions, classes, variables), attributes (e.g., names, locations, modifiers), and relations among them (e.g., containment, calls, inheritance), in a form suitable for systematic querying and inference. These facts are mechanically extracted by language-specific frontends, for example through abstract syntax tree traversal, and provide a machine-readable structured abstraction of the repository. Importantly, program facts are \emph{descriptive}: they record what is present in the program, rather than how analyses should be performed.

Datalog is a declarative logic programming language rooted in first-order logic and database theory. A Datalog specification consists of rules that describe how new facts can be derived from existing ones.
\begin{definition}[Datalog Rule]
A Datalog rule has the form:
\begin{equation}
    \begin{aligned}
    R_0(t_1, \ldots, t_k) \leftarrow {} & R_1(u_1^{(1)}, \ldots, u_{m_1}^{(1)}), \ldots, 
                                       & R_n(u_1^{(n)}, \ldots, u_{m_n}^{(n)})
    \end{aligned}
\end{equation}
where $R_0$ is the head predicate and $R_1,\ldots,R_n$ are body predicates. Each argument $t_j$ or $u_j^{(i)}$ is a constant or variable.
\end{definition}

For any assignment of variables to constants that makes all body atoms simultaneously true, the corresponding instantiated head atom is also true. By repeatedly applying such rules to a fixed set of ground facts, Datalog computes derived facts until a least fixpoint is reached. This makes it well suited for expressing repository-level structural properties, such as reachability, dependency propagation, containment, and pattern constraints.

In this setting, extracted program facts are ground predicate instances over which synthesized Datalog rules are evaluated. For example, Figure~\ref{fig:example-dataloc} shows a \texttt{function\_\allowbreak definition} predicate for recording function-level facts.

A localization query can then be expressed as a rule over these facts, allowing a reasoning engine such as \souffle to infer precise code locations from structural constraints rather than relying on surface-level keyword matching.

\subsection{Motivating Example}\label{sec:example-dataloc}

Figure~\ref{fig:example-dataloc} illustrates a motivating example of KA-LCL. Given a natural language query, the LLM translates the question's intent and constraints into a Datalog program over two types of facts: \textit{Extensional Database (EDB)} facts, such as \texttt{function\_definition}, which are extracted directly from source code, and \textit{Intensional Database (IDB)} facts, such as \texttt{LargeFunctions}, which are derived through logical inference. Executing the rule with \souffle yields precise matching code locations. This example highlights the key division of labor in the approach: the LLM bridges natural language and formal logic, while Datalog performs deterministic reasoning over repository structure to ensure sound and complete results.
