\section{Evaluation}\label{sec:eval-mpchecker}
This section describes the evaluation of \toolchecker. It first presents the research questions, then details the experiment setup and evaluation subjects. Finally, it analyzes the experimental results and answers each research question. The evaluation was guided by the following research questions:

\begin{enumerate}
  \item \textbf{RQ1:} How accurate is \toolchecker in extracting constraints from API documentation?
  \item \textbf{RQ2:} How effective is \toolchecker in detecting errors related to multi-parameter constraints in API documentation?
  \item \textbf{RQ3:} How effectively can \toolchecker detect unknown inconsistency issues?
\end{enumerate}

\subsection{Experiment Setup}
\subsubsection{Dataset.}
There is currently no well-established dataset specifically focusing on multi-parameter API
documentation errors. To better evaluate the effectiveness of the tool, two datasets were constructed: a constraint dataset and an inconsistency dataset.

\paragraph{Constraint Dataset.}
The constraint dataset contains 72 constraints from 4 popular open-source data science libraries with well-maintained documentation, including \texttt{scikit-learn}, \texttt{scipy}, \texttt{numpy}, and \texttt{pandas}. The constraints were gathered by analyzing commits from each GitHub repository, focusing on developers' modifications to documentation related to multi-parameter constraints. To streamline this process, an automated script was developed to collect all documentation-related commits and identify changes within parameter (including attribute) descriptions, adhering to two distinct docstring styles (see details in \fref{fig:docstring}). By mapping parameter names to their descriptions, it then cross-checks if any parameter names appear within others' descriptions to keep potential constraint-related documentation. Approximately 90\% to 95\% of irrelevant commits were excluded, leaving a smaller subset of commits that may contain constraints. Additionally, random sampling of the excluded commits was performed to assess and minimize the impact of this heuristic. Despite the approach's proven effectiveness, the remaining subset still contains a substantial number of submissions. Each of the four repositories has over 30,000 commits, requiring manual verification of approximately 1,500 commits per repository to further identify multi-parameter constraints. For each constraint, its source information (repository name, SHA, file path, etc.) was logged and the code file was retained, enabling swift extraction of documentation and code for reproducibility.
In some cases, the condition enforcing the constraint is located not in the current function but in a function it calls, leading to a mismatch between documentation and code. To address this, such mismatches were recorded and the constraint description was relocated to the function where the check actually occurs.




\paragraph{Inconsistency Dataset.}
Based on the constraint dataset, an inconsistency dataset was constructed comprising 126 multi-parameter constraints that lead to code-documentation inconsistencies. An analysis of around 20 resolved GitHub issues related to multi-parameter constraints identified eight common patterns that may cause CDI: (1) Parameter name change; (2) Value Change; (3) Logic Change; (4) Remove Parameter; (5) Add Constraints; (6) Remove Constraints; (7) Missing Documentation; (8) Modify Description. To better evaluate the capabilities of the tool, these eight patterns were applied to mutate the dataset based on the \emph{Constraint Dataset}. For each constraint, two types of modifications were applied, resulting in an inconsistency dataset containing 216 constraints. The mutated constraints and the original constraints were fed into an SMT solver to verify if the mutations violate the original constraints. Each of them was also manually inspected to ensure the constraint was inconsistent. It is important to note that modifying a correct constraint does not necessarily turn it into an incorrect one. As a result, the process yielded an \emph{Inconsistency Dataset} containing 126 inconsistent constraints and 90 consistent constraints. In a sense, the dataset can be considered as potential inconsistencies that may realistically occur during development.

\subsubsection{Subjects}
\tref{tab:subjects} lists 7 popular libraries on which \toolchecker was evaluated, the first four for dataset construction and the last three for assessing \toolchecker's ability to detect unknown issues. The selected libraries are of high quality and widely used, with tens of thousands of stars on GitHub. These libraries are substantial third-party libraries, averaging 1,642 classes, 14,467 functions, with an average of 373.6 thousand lines of code, and each function containing an average of 1.3 parameters. The tool extracts documentation constraints and path constraints from these libraries and uses a fuzzy constraint reasoner to detect inconsistencies.

\toolchecker was implemented in Python. All the experiments were performed on an Intel(R) Xeon(R) Silver 4214 CPU @ 2.20GHz machine with 252GB of RAM, running Ubuntu 18.04, with Python 3.8.19 and Z3 4.13.0.
For the constraint extraction evaluation (RQ1), GPT-4 was accessed through OpenAI's API. For result validation, given the absence of established benchmarks in this domain, two volunteer researchers independently reviewed the constraint extraction results from GPT-4, manually assessing each constraint's consistency with the original Python documentation. Any discrepancies were resolved through consensus discussion. In RQ1, \textit{Equivalent} denotes a correctly extracted constraint that preserves the meaning of the original documentation, whereas \textit{Non-Equivalent} groups incorrect extractions and missing constraints. Thus, these categories assess documentation constraint extraction, rather than equivalence between documentation and code constraints.


\subsection{Results}
\subsubsection{Accuracy of LLM in extracting constraints from API documentation.}
\tref{tab:rq1} displays the result of RQ1. The experiment shows that the tool correctly identified and extracted 66 out of 72 constraints contained in the Python documentation collected in the benchmark, achieving an accuracy of 91.7\%, which demonstrates that the tool can successfully extract most of the constraints accurately, with few errors or omissions.
Next, the remaining failed cases are examined to investigate the reasons for the inaccuracy. The analysis showed that out of the 6 extraction failures, 4 involved missing constraints during the documentation processing. For example, one of the missing constraints is: ``(batch\_size = auto) $\rightarrow$ (batch\_size = min(200, n\_samples))''. Although this case involves a constraint between multiple parameters, the format is tricky because one of the parameters is within a function, which may have misled GPT-4 and caused it to miss this constraint during extraction. In the last 2 cases, the constraint information was identified but converted into incorrect logic expressions due to the complex logic or sentence structure.

An ablation study further explores \toolchecker's abilities. The results show that \toolchecker without few-shot learning achieves an accuracy of 62.5\%. Most failures occur in the incorrect extraction of constraints. This indicates that including few-shot learning is important for \toolchecker to generate accurate constraints.
Next, \toolchecker without applying chain-of-thought techniques results in an accuracy of 79.2\%, with the number of missed constraints accounting for more than half of total non-equivalent cases. This suggests that GPT tends to miss more details in documentation when chain-of-thought is removed.
After including chain-of-thought and few-shot learning, \toolchecker's performance shows a clear improvement.

% ===== RQ2 =====
\subsubsection{\toolchecker's effectiveness in detecting multi-parameter API documentation errors}
To measure \toolchecker's effectiveness in detecting multi-parameter API documentation errors, \toolchecker was evaluated on the inconsistency dataset. \tref{tab:res} shows the results of \toolchecker in detecting multi-parameter CDI on the inconsistency dataset.

The \vanillatool does not include fuzzy words or apply fuzzy constraint satisfaction theory, limiting its ability to handle implicit constraints. Despite these limitations, it achieved an impressive 69\% recall by detecting 87 inconsistencies. With fuzzy words and fuzzy constraint logic, \toolchecker's performance significantly improved, successfully identifying 117 inconsistencies with a recall of 92.8\% and  an accuracy $=\frac{TP+TN}{TP+TN+FP+FN}=\frac{117+88}{216}=94.9\%$. This demonstrates that incorporating fuzzy words and fuzzy constraints can expand the range of detectable constraints. However, two false positives were identified because the constraints lie between the parameters and method calls, rather than among the parameters. One example is shown below:


% \texttt{$($shape $=$ None$)$ $\wedge$ $($axes $\neq$ None$)$ $\rightarrow$ $($shape $=$ numpy.take$($x.shape,axes,axis=0$))$}
\(
(\mathtt{shape}=\mathtt{None}) \land
(\mathtt{axes}\neq\mathtt{None}) \rightarrow
(\mathtt{shape}=\mathtt{numpy.take(x.shape,axes,axis=0)})
\)


where the value of ``shape'' is the return value of the function ``take()'' from the NumPy library. Modern software increasingly emphasizes code maintainability and reusability, leading to highly complex function calls, often involving nested or chained calls. To avoid the high risk of path explosion in symbolic execution, \toolchecker replaces function calls with symbolic inputs during the preprocessing phase, which leads to misclassification of these two inconsistencies.



The remaining 9 unresolved inconsistent constraints stem from external function dependencies. While incorporating external function code could resolve these constraints, this approach risks infinite recursive dependencies and path explosion. This study takes the view that constraints should be handled within the documented function itself.

A notable situation arose during one issue report: even though the issue had been confirmed, one developer expressed dissatisfaction. He believed the reporters were an automated tool or AI-based bot because of their anonymous status, which diminished his enthusiasm for addressing the issue. With a mass of LLM-based program analysis or inconsistency checkers now available, while they offer insights sometimes, their results often cost more manual verification than traditional tools due to higher uncertainty.

\paragraph{Comparative Study.}
Therefore, a comparative experiment was conducted between the tool and the approach of using only LLMs as a constraint checker on the same dataset. To align with the experiment settings, GPT-4, one of the leading models, was selected for comparison and evaluated under two settings: 1) LLM: providing the raw documentation and code as input, directly prompting GPT to check for consistency, and 2) LLM+C: first extracting constraints using the LLM and then providing both these constraints and their corresponding code to the LLM for a consistency check. In addition, the LLM was also required to provide justifications for its answers.


As shown in \tref{tab:res}, when raw documentation and the corresponding code were provided as inputs to the LLM, the LLM demonstrated significant limitations in detecting multi-parameter CDIs, finding only 7 inconsistencies with a recall of 5.6\%. When extracted constraints and code were given as inputs, LLM+C demonstrated heightened awareness of the task and had a higher probability of locating the constraint-related code segments. However, it still struggled to determine inconsistency. Out of 126 inconsistent constraints, 52 were identified correctly, yielding a recall of 41.3\%. After a thorough review of the LLM's responses, the analysis showed that LLM+C gave correct results in many cases but provided unreasonable or even wrong explanations. These results demonstrate that the LLM still has limitations in detecting complicated multi-parameter CDIs, highlighting that the method’s design is the key factor in enhancing detection performance rather than any reliance on potential pretraining data leakage.

Notably, \fuzzytool demonstrated a 23.8\% higher recall than \vanillatool, substantiating the effectiveness of the implementation of fuzzy words and fuzzy constraint logic.

\subsubsection{Practical effect of \toolchecker}
The tool's effectiveness in detecting unknown multi-parameter inconsistencies was validated by manual review and developer feedback. Fourteen inconsistencies identified by \toolchecker were reported to the library maintenance team and received positive engagement and warm responses. Two of them even sparked further discussions about potential issues. This not only affirmed the reports' quality but also reflected the enthusiasm of the open-source community.

For example, an issue confirmed by the \texttt{scikit-learn} team originates from the independent function ``lars\_path'', as shown in \fref{fig:eg3}. Apparently, an inconsistency exists between the documentation and code regarding whether ``Gram'' is None when ``X'' is None. Therefore, the issue report~\cite{issue30099} detailed the inconsistent documentation sections alongside the corresponding code snippet. The developer made a bit of archeology, admitted the documentation needed to be updated, and asked whether the reporters would submit a PR to correct this error. Finally, the documentation description was fixed to ``If X is None, Gram must also be None''.

For most issue reports, feedback was received promptly, and 11 inconsistencies were confirmed and improvements were made to documentation or code. Of the remaining three cases, two were reported at the initial phase of the experiments, when the understanding of the project architecture was still insufficient. The checks for these two constraints were implemented in other deeper files and could not be accurately verified at that time. The third inconsistency stemmed from ambiguity in the natural language, which resulted in a different interpretation that diverged from the developers' original intent. Furthermore, these reported issues have contributed to four DS/ML repositories (\texttt{scikit-learn}, \texttt{keras}, \texttt{statsmodels}, \texttt{dask}), which emphasizes the generalization of the tool.

At the time of writing, 10 out of 11 confirmed inconsistencies have been resolved: 7 through documentation fixes and 3 through updates to both documentation and code. This aligns with intuition: code errors are more likely to cause runtime failures and are thus easier to detect, whereas documentation errors and their potential efficiency impacts are often subtler and harder to identify.
